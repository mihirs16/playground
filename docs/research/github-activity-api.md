# Research: GitHub API as a source for "what I'm currently working on"

**Date**: 2026-07-25
**Question**: What is the right GitHub API source for a live "currently working on" feed on a personal site, and what does it cost in rate limits, auth scope, and privacy?

## Bottom line

- **Use `GET /users/{username}/events/public`, polled with conditional requests (ETag), authenticated with a fine-grained PAT.** It is the only source that reflects recent *activity* (pushes, PR/issue opens, reviews) rather than a coarse timestamp or an annual aggregate. [docs.github.com/en/rest/activity/events](https://docs.github.com/en/rest/activity/events?apiVersion=2022-11-28)
- **GitHub explicitly disclaims real-time freshness on that endpoint**: "This API is not built to serve real-time use cases. Depending on the time of day, event latency can be anywhere from 30s to 6h." — plan the UI copy ("recently", not "right now") around this. [docs.github.com/en/rest/activity/events](https://docs.github.com/en/rest/activity/events?apiVersion=2022-11-28)
- **A fine-grained PAT with zero permissions granted still gets the full 5,000 req/hour authenticated limit** and always retains read-only access to public repos/activity — no scope needs to be requested for a public-only feed. [docs.github.com/en/authentication/.../managing-your-personal-access-tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)
- **304 Not Modified responses from conditional (ETag) requests do not count against the primary rate limit**, provided the request is authenticated — this makes cheap, frequent polling viable even at hobby scale. [docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)
- **Aggregate private-activity counts are possible without leaking repo names**, via GraphQL `contributionsCollection.restrictedContributionsCount`, but only if the token owner has enabled "Include private contributions on my profile" — otherwise the field is 0 regardless of token scope. [docs.github.com/en/graphql/reference/users](https://docs.github.com/en/graphql/reference/users)
- **`pushed_at` on the repo object is not documented precisely** — GitHub's schema only types it as a timestamp with no description of what git operations update it. Treat any claim about its exact update semantics as community-reported, not GitHub-confirmed.

## 1. Candidate sources

### `GET /users/{username}/events/public`

- Returns up to **300 events**, and **only events from the past 30 days** ("Events older than 30 days will not be included even if the total number of events in the timeline is less than 300"). This corrects an initial assumption of a 90-day window — the documented cutoff is 30 days. [docs.github.com/en/rest/activity/events](https://docs.github.com/en/rest/activity/events?apiVersion=2022-11-28)
- Supports `per_page` (max 100, default 30) and `page` pagination. [docs.github.com/en/rest/activity/events](https://docs.github.com/en/rest/activity/events?apiVersion=2022-11-28)
- Documented freshness: **"This API is not built to serve real-time use cases. Depending on the time of day, event latency can be anywhere from 30s to 6h."** This is the single most decision-relevant sentence in this research — a "currently working on" widget built on this endpoint can lag by hours. [docs.github.com/en/rest/activity/events](https://docs.github.com/en/rest/activity/events?apiVersion=2022-11-28)
- Event types themselves (PushEvent, PullRequestEvent, IssuesEvent, etc.) are enumerated on GitHub's separate [webhook/event payload docs](https://docs.github.com/en/rest/using-the-rest-api/github-event-types), not repeated inline on the events-listing page.

### `GET /users/{username}/received_events/public`

- Same endpoint family and same 30-day/300-event/latency characteristics as `events/public`, but returns events *directed at* the user (e.g. issues they're mentioned in, activity in repos they watch) rather than events *performed by* them. [docs.github.com/en/rest/activity/events](https://docs.github.com/en/rest/activity/events?apiVersion=2022-11-28)
- **Judgement**: wrong endpoint for "what I'm working on" — it reflects others' activity toward the user, not the user's own output.

### `GET /users/{username}/repos?sort=pushed` and `pushed_at`

- The endpoint documents `sort=pushed` as a valid option and `pushed_at` as a `string or null, format: date-time` field on the repository schema, but **GitHub's reference does not define what git operation sets it** — no statement on whether it updates for pushes to non-default branches, tag-only pushes, or force-pushes, and no statement about fork behavior. [docs.github.com/en/rest/repos/repos](https://docs.github.com/en/rest/repos/repos?apiVersion=2022-11-28)
- **Not documented by GitHub; community-reported**: widely observed behavior (Stack Overflow / community discussions, not cited here as authoritative) is that `pushed_at` updates on pushes to *any* branch, not just default, and does update for tag pushes. Do not rely on this for correctness — verify empirically if the distinction matters to the design.
- **Judgement**: even if precisely defined, `pushed_at` alone only gives a per-repo "last touched" timestamp with no signal about *what* was done or how much — noisier and less meaningful than the events feed, but cheaper (one list call instead of parsing an event stream) and immune to the 30-day cutoff. Reasonable as a fallback/enrichment (e.g., "last active repo") rather than a primary feed.

### GraphQL `User.contributionsCollection`

- Arguments `from`/`to` are DateTime, and **if omitted, `from` defaults to a year ago and `to` defaults to one year after `from` (or now)** — implying the natural query span is bounded to roughly a year; the docs don't state a hard max span enforced server-side beyond this default behavior. [docs.github.com/en/graphql/reference/users](https://docs.github.com/en/graphql/reference/users)
- Fields include `totalCommitContributions`, `totalIssueContributions`, `totalPullRequestContributions`, `totalPullRequestReviewContributions`, `contributionCalendar` (the calendar heatmap), and `commitContributionsByRepository` (per-repo commit breakdown). [docs.github.com/en/graphql/reference/users](https://docs.github.com/en/graphql/reference/users)
- Private-contribution fields: `restrictedContributionsCount` — "a count of contributions made by the user that the viewer cannot access. Only non-zero when the user has chosen to share their private contribution counts" — plus `hasAnyRestrictedContributions`, `earliestRestrictedContributionDate`, `latestRestrictedContributionDate`. [docs.github.com/en/graphql/reference/users](https://docs.github.com/en/graphql/reference/users)
- **Judgement**: this is an aggregation API (counts, calendar density), not an activity stream — good for "N commits this week" style ambient stats, wrong for "here's the specific thing I just did."

### GraphQL `repository.defaultBranchRef.target.history`

- Not separately re-verified beyond schema structure (well-established Commit `history` connection on a `Ref`'s `target`), gives the actual commit list on the default branch of one named repo — freshest and most precise, but requires the poller to already know which repo(s) to watch, and it only sees the default branch (misses feature-branch work in progress, which is arguably the truest "currently working on" signal).

### Recommendation (judgement)

For "what I'm currently working on": **poll `events/public` on a schedule (e.g. every few minutes) with `If-None-Match` conditional requests**, filter to `PushEvent`/`PullRequestEvent`/`IssuesEvent`/`CreateEvent`, and accept the documented 30s–6h latency in the UI framing. Use `contributionsCollection` only for an ambient "N contributions this month" stat, not as the live feed, since it's an aggregate, not a stream. Do not build the primary feed on `pushed_at` — it's cheap but its semantics are undocumented and its signal is coarser than events.

## 2. Auth and rate limits

- **Unauthenticated REST**: 60 requests/hour, per originating IP. [docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api?apiVersion=2022-11-28)
- **Authenticated REST (PAT, OAuth app, GitHub App as standard user)**: 5,000 requests/hour. [docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api?apiVersion=2022-11-28)
- **GraphQL**: separate point-based budget, **5,000 points/hour per user** (10,000 for GitHub Enterprise Cloud members); GitHub App installations get 5,000–12,500 points/hour depending on repo/user counts; GitHub Actions tokens get 1,000 points/hour/repo. [docs.github.com/en/graphql/overview/rate-limits-and-node-limits-for-the-graphql-api](https://docs.github.com/en/graphql/overview/rate-limits-and-node-limits-for-the-graphql-api)
- **GraphQL point calculation**: cost is visible via the `rateLimit.cost` field on the response; can be estimated by summing requested connection nodes, dividing by 100, rounding to the nearest whole number (minimum 1). Node limit per call is 500,000 total nodes (nodes multiply across nested connections). [docs.github.com/en/graphql/overview/rate-limits-and-node-limits-for-the-graphql-api](https://docs.github.com/en/graphql/overview/rate-limits-and-node-limits-for-the-graphql-api)
- **Secondary limits**: no more than 100 concurrent requests across REST+GraphQL combined; REST secondary limit is 900 points/minute (GET/HEAD/OPTIONS = 1 point, POST/PATCH/PUT/DELETE = 5 points); GraphQL secondary limit is 2,000 points/minute, with mutations costing 5 points and content-generating requests (e.g. creating issues/comments) capped at 80/minute. [docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api?apiVersion=2022-11-28), [docs.github.com/en/graphql/overview/rate-limits-and-node-limits-for-the-graphql-api](https://docs.github.com/en/graphql/overview/rate-limits-and-node-limits-for-the-graphql-api)
- **Does `events/public` behave differently authenticated vs not?** Not established from the primary events-doc page itself beyond the general REST rate-limit split above (60/hr unauth vs 5,000/hr auth applies to this endpoint like any other REST endpoint) — no endpoint-specific carve-out was found in the fetched docs. Treat any claim of a *content* difference (e.g., seeing more event types when authenticated as the same user) as **not established here**; worth a targeted follow-up if the design depends on it.

## 3. Minimum permission for public-activity-only

- **Fine-grained PAT**: "Tokens always include read-only access to all public repositories on GitHub." [docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens) A fine-grained PAT with **zero repository/account permissions selected** is exactly this "public read-only" token, and it authenticates as a normal PAT for rate-limit purposes — i.e. it gets the standard 5,000 req/hour authenticated budget, not the 60/hour unauthenticated one. (The specific permissions-required reference page for fine-grained PATs states permissions "are required to access private resources" and that "some endpoints can also be used to access public resources without these permissions," consistent with a no-permission token still working for public data.) [docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens)
- **Classic PAT scopes**: `public_repo` grants write+read to public repos (broader than needed for a read-only feed) and `read:user` grants read access to profile data; no classic scope corresponds to "public read-only, nothing else" as cleanly as an empty fine-grained PAT does — the fine-grained token is the tighter-scoped choice for this use case. **Judgement**: prefer a fine-grained PAT with no permissions over any classic scope for this poller.
- **GitHub App installation tokens**: rate limits scale with installation size (5,000–12,500 points/hour per the GraphQL rate-limit doc above; REST-side GitHub App installation tokens follow a comparable higher-than-5,000 ceiling tied to repo/org size per GitHub's docs) — materially better only at multi-repo/org scale. For a single-user personal-site poller hitting one account's public events, a fine-grained PAT's 5,000/hour is already far more headroom than needed (polling every minute is 1,440 requests/day, ~2% of the hourly budget if requests were not amortized by 304s, and near-zero once conditional requests kick in).

## 4. Private activity without leaking repo names

- `restrictedContributionsCount` on `contributionsCollection` gives a count-only signal, but it is **"only non-zero when the user has chosen to share their private contribution counts"** — this is the profile setting "Include private contributions on my profile." If that setting is off, the field returns 0 to every caller including the account owner's own authenticated token, regardless of what permissions the token holds. [docs.github.com/en/graphql/reference/users](https://docs.github.com/en/graphql/reference/users)
- If the setting is **on**, `restrictedContributionsCount` / `hasAnyRestrictedContributions` / the calendar's private-day counts become visible to any viewer (not just the token owner) — this is a profile-wide visibility toggle, not a per-token grant. So "counts only, no names" for private repos is achievable, but it's controlled by a GitHub account setting rather than by scoping the API token narrowly.
- A token with actual private-repo read access (`repo` scope classic, or fine-grained `Contents: Read` on specific private repos) can retrieve full repo names, commit messages, and diffs from those repos — i.e., **the token boundary and the "no repo names leaked" boundary are different controls**: for a personal site meant to publish only aggregate private activity, the safer design is to keep the poller's token public-only (no permissions) and rely on `restrictedContributionsCount` (which needs no private-repo grant at all, since it's computed server-side from the account's own private activity when the profile setting is on) — this avoids ever handing the site's poller a token that *can* read private repo contents.

## 5. Conditional requests / ETags

- **"Making a conditional request does not count against your primary rate limit if a 304 response is returned and the request was made while correctly authorized with an Authorization header."** [docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)
- Mechanism: send `If-None-Match` with a previously returned `ETag` (or `If-Modified-Since` with `Last-Modified`); an unchanged resource returns `304 Not Modified`. [docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)
- Caveat: conditional requests are **not supported for unsafe methods** (POST/PUT/PATCH/DELETE) except where an endpoint's docs say otherwise — irrelevant here since the poller only does GETs. [docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)
- **Design implication**: a poller hitting `events/public` every 1–2 minutes with ETag caching costs effectively nothing against the 5,000/hour budget on the steady state (only the first request and requests after genuine new events consume the primary limit); this makes frequent polling cheap and safe even well within GitHub's secondary 900-points/minute REST ceiling.

## 6. Terms

- GitHub's Acceptable Use Policies define **scraping** ("extracting information from our Service via an automated process, such as a bot or webcrawler") as explicitly distinct from API usage: **"Scraping does not refer to the collection of information through our API."** — using the documented REST/GraphQL APIs is not "scraping" under this policy. [docs.github.com/en/site-policy/acceptable-use-policies/github-acceptable-use-policies](https://docs.github.com/en/site-policy/acceptable-use-policies/github-acceptable-use-policies)
- Prohibited regardless of channel: using data obtained "whether scraped, collected through our API, or obtained otherwise" **"for spamming purposes, including for the purposes of sending unsolicited emails to users or selling personal information"** — not applicable to a personal-site activity widget, which only redisplays the account owner's own public activity. [docs.github.com/en/site-policy/acceptable-use-policies/github-acceptable-use-policies](https://docs.github.com/en/site-policy/acceptable-use-policies/github-acceptable-use-policies)
- The acceptable-use page points to **"Section H of our Terms of Service for our API Terms"** for API-specific rules; that section's full text was not retrieved in this pass — flagged below as an open item, though nothing found so far suggests caching/display of one's own public activity on a personal site is restricted.
- Rate-limit-abuse language (found under the REST rate-limits doc, adjacent to but part of the same policy family): excessive/abusive request patterns can lead to **temporary suspension of API access**, with GitHub attempting to warn via email first, and **sharing API tokens to collectively exceed rate limits is prohibited** — neither is a concern for a single low-frequency personal poller using its own token. [docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api?apiVersion=2022-11-28)

## Open / undocumented

- **`pushed_at` update semantics** (any branch vs. default branch only, tag pushes, forks) — GitHub's REST reference types the field but gives no description of what git operations set it. Not documented by GitHub; only community-reported behavior exists. Verify empirically before relying on it.
- **Whether `events/public` returns different content when called authenticated as the subject user vs. as a third party** (e.g., does the account owner see anything a stranger wouldn't, given it's already scoped to "public" events) — not found in the fetched docs; the general REST auth/rate-limit split clearly applies, but a content difference specific to this endpoint was not confirmed or ruled out.
- **Full text of Terms of Service Section H ("API Terms")** — the acceptable-use policy explicitly defers detailed API terms to this section, which was not fetched in this pass. Worth a follow-up read before treating the ToS analysis as complete, though nothing surfaced so far is a blocker.
- **Exact hourly-since-epoch behavior of the 30-day event window edge case** — e.g. whether the 30-day cutoff is a rolling wall-clock window or resets on some other cadence — the docs state the rule but don't detail internal refresh timing beyond the 30s–6h latency figure already cited.

None of the above open items look likely to overturn the recommendation in "Bottom line," but the ToS Section H gap and the `pushed_at` semantics gap are the two worth closing before finalizing an implementation that leans on either.
