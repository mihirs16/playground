# Web Components Strategy for `blank` — Research Findings

**Scope**: Primary-source facts to inform the Lit-vs-vanilla and Shadow-vs-light-DOM decisions for `blank`, a minimal monotone Web Components UI library consumed by `persona` (a static site) and other personal projects. This document is facts only; the decision is downstream.

## Executive summary

Lit's own site states its runtime is **~5 KB minified+gzipped** (lit.dev homepage), built on reactive properties (attribute↔property sync, batched async re-render), `html` tagged-template rendering with fine-grained DOM diffing, standard custom-element lifecycle, and a directive system — all of which a vanilla `HTMLElement` author must hand-write (getters/setters, `attributeChangedCallback`/`observedAttributes` wiring, update batching, template diffing). The cost is a runtime dependency every consumer loads, a version to keep in sync, and a possible duplicate-Lit-versions problem if two dependencies pin different major versions. Lit's own docs actively discourage rendering into light DOM ("generally not recommended... will not have access to DOM or style scoping"), i.e. Shadow DOM is the default best practice, but Shadow DOM trades composability/theming ease for encapsulation — CSS custom properties do cross the shadow boundary by inheritance, and `::part()`/`::slotted()` are the sanctioned but limited theming escape hatches. Constructable stylesheets (`adoptedStyleSheets`) are Baseline-widely-available since March 2023 and directly solve per-instance style duplication by sharing one `CSSStyleSheet` object across many shadow roots. Declarative Shadow DOM (DSD) reached Baseline "Newly available" across Chromium, Firefox and WebKit as of August 5, 2024 (Firefox 123+, Safari 16.4+), making SSR/static-prerendering of shadow-DOM markup viable without JS — but Lit's own SSR package (`@lit-labs/ssr`) is explicitly labeled Labs/experimental with named production-readiness caveats. React 19 shipped full native custom-element interop (100% on Custom Elements Everywhere) fixing the historic props-vs-attributes and event-handling gaps; Vue, Svelte, and Astro all have mature, documented custom-element support, so no mainstream consumer is foreclosed by choosing Web Components.

## 1. Lit vs vanilla custom elements at small scale

**What Lit provides:**
- **Reactive properties**: declaring a property (via `@property()` decorator or static `properties` field) gets you an observed attribute and property↔attribute sync automatically — "By default, Lit sets up an observed attribute corresponding to each public reactive property, and updates the property when the attribute changes," with optional reflection back to attributes for CSS visibility ([Lit docs — Reactive properties](https://lit.dev/docs/components/properties/)).
- **Batched re-render**: "an update is scheduled asynchronously. If an update is already scheduled, only a single update is executed" — i.e. multiple property writes in the same tick coalesce into one render ([Lit docs — Reactive properties](https://lit.dev/docs/components/properties/)).
- **`html` templating with efficient DOM updates**: Lit's `lit-html` templating library does fine-grained, expression-level DOM diffing/patching rather than full re-parse (core value prop stated across Lit docs; see [lit.dev](https://lit.dev/)).
- **Lifecycle**: Lit components still use the standard custom-element lifecycle (`connectedCallback`, etc., per the platform — see §item 1 vanilla lifecycle below) plus Lit's own `willUpdate`/`update`/`updated`/`firstUpdated` reactive-update lifecycle layered on top ([Lit docs — Reactive properties](https://lit.dev/docs/components/properties/)).
- **Directives**: a documented extensibility system for custom template-value behaviors (`lit/directives/*`).
- **Actual bundle size**: Lit's own homepage states the library weighs **"5 KB (minified and compressed)"** ([lit.dev](https://lit.dev/)). (Community sources further break this down as ~2.7 KB for the `lit-html` templating layer alone and ~5.8 KB including the full component base — these are secondary corroboration, not the cited claim.)

**What it costs:**
- A runtime dependency shipped to (or required by) every consumer of `blank` — every page loading a `blank` component loads Lit unless it's inlined/bundled per-component.
- A version to keep current; Lit follows semver as a separate package from `blank`.
- Potential duplicate-Lit-versions problem: if two different dependencies in a consumer's tree pin incompatible major versions of Lit, bundlers can ship two copies of the runtime unless deduped (a well-known class of issue for any shared runtime dependency; not specific to Lit but structurally identical to how e.g. React duplication issues arise).

**Is vanilla `HTMLElement` sufficient at small scale?** The vanilla platform requires hand-writing what Lit automates:
- **Property/attribute sync**: implement `static observedAttributes`, `attributeChangedCallback(name, oldValue, newValue)`, and manual getters/setters that call `setAttribute()`/`getAttribute()` yourself — MDN documents the lifecycle callbacks (`connectedCallback`, `disconnectedCallback`, `adoptedCallback`, `attributeChangedCallback`, plus the newer `connectedMoveCallback`) and states the developer must implement `observedAttributes` and `attributeChangedCallback` manually to react to attribute changes, including on initial parse ([MDN — Using custom elements](https://developer.mozilla.org/en-US/docs/Web/API/Web_components/Using_custom_elements)).
- **Batched re-render**: vanilla elements re-render however you write your render function; you must debounce/microtask-batch yourself if multiple attribute/property writes happen synchronously.
- **Template diffing**: vanilla has no built-in efficient-update primitive; naive `innerHTML =` re-parses and destroys/recreates the whole subtree (losing focus, animation state, event listeners) unless you hand-write a diffing layer or hand-write imperative DOM patches per property.

For a genuinely small, monotone component set, all three of these are tractable to hand-write, but each is a place for the library to hand-roll and maintain "reactive property," "batched update," and "diffing" concepts that Lit ships pre-built at ~5 KB.

**Bottom line**: Lit's cost is a small (~5 KB), semver-tracked runtime dependency; its benefit is that property/attribute sync, update batching, and template diffing come for free instead of being hand-written and hand-maintained by `blank`.

## 2. Shadow DOM vs light DOM

**Shadow DOM encapsulation guarantees** (MDN, [Using shadow DOM](https://developer.mozilla.org/en-US/docs/Web/API/Web_components/Using_shadow_DOM)):
- **DOM scoping**: `document.querySelectorAll()` and similar page-level DOM APIs cannot see into a shadow root; "code running in the page cannot accidentally break a custom element by modifying its internal implementation."
- **Style scoping**: page-level CSS does not affect elements inside a shadow root, and shadow-root styles do not leak out to the page — eliminating selector collisions in both directions.
- `mode: "open"` vs `"closed"` controls only whether `element.shadowRoot` is script-accessible from outside; MDN notes this "is not strong security... can be evaded."

**Lit's own guidance** ([Lit docs — Working with Shadow DOM](https://lit.dev/docs/components/shadow-dom/)):
- Documents the same three benefits (DOM scoping, style scoping, composition via the host/children split).
- Light DOM is supported only by overriding `createRenderRoot()` to return `this`, and Lit's docs explicitly warn: **"Rendering into children and not shadow DOM is generally not recommended. Your element will not have access to DOM or style scoping, and it will not be able to compose elements into its internal DOM."**
- If rendering into light DOM, "Lit has no way to encapsulate your component stylesheets anymore... your light components will now inherit styles from the root that they are contained in."

**Theming/SSR friction Shadow DOM introduces**: encapsulation that blocks page CSS from reaching inside also blocks a consumer's ad-hoc theme overrides unless the library deliberately exposes custom properties, `::part()`, or `::slotted()` hooks (see §5). Historically Shadow DOM also blocked server-rendering encapsulated markup without JS — this is now addressed by Declarative Shadow DOM (see §4).

**Light DOM with prefixed classes**: gives full page-CSS themeability (any consumer CSS can target the classes) but forfeits both scoping guarantees above — global CSS can leak in, and library-internal class names leak out as public API surface (any class name becomes something consumers can accidentally (or deliberately) depend on/collide with).

**Current state of practice**: Lit's documentation (the dominant first-party Web Components authoring layer) treats Shadow DOM as the default and light-DOM rendering as an explicitly discouraged escape hatch. Neither WHATWG DOM/HTML nor W3C publishes a "recommended" stance on Shadow vs. light DOM as a design pattern (that is a library/author-level decision, not a spec position) — the specs merely define both mechanisms exist (`attachShadow()`, slotting) without endorsing one over the other for component authoring.

**Bottom line**: Shadow DOM is the documented default best practice per the dominant first-party tooling (Lit); light DOM is a known, explicitly-flagged-as-discouraged tradeoff that trades encapsulation for theming ease, and the class-name-leakage cost is a public-API commitment problem for a library that must not become consumer-specific.

## 3. Constructable stylesheets / `adoptedStyleSheets`

- **What it is**: `new CSSStyleSheet()` plus `.replaceSync()`/`.replace()` lets you construct a stylesheet object in JS and assign it to `Document.adoptedStyleSheets` or `ShadowRoot.adoptedStyleSheets`; the same `CSSStyleSheet` instance can be adopted by multiple documents/shadow roots simultaneously, and mutating it updates all adopters at once ([MDN — Document.adoptedStyleSheets](https://developer.mozilla.org/en-US/docs/Web/API/Document/adoptedStyleSheets)).
- **Browser support**: MDN marks this **"Baseline: Widely available... available across browsers since March 2023"** ([MDN — Document.adoptedStyleSheets](https://developer.mozilla.org/en-US/docs/Web/API/Document/adoptedStyleSheets)).
- **Does it solve per-instance style duplication?** Yes, directly: without adopted stylesheets, each `<style>` tag placed inside each shadow root is a separate parsed/stored stylesheet per component instance. With `adoptedStyleSheets`, one `CSSStyleSheet` object is constructed once and shared by reference across every instance's shadow root — MDN's own example constructs a single `sheet`, then assigns `shadow1.adoptedStyleSheets = [sheet]` and `shadow2.adoptedStyleSheets = [sheet]`, noting a rule change to `sheet` is reflected in both ([MDN — Document.adoptedStyleSheets](https://developer.mozilla.org/en-US/docs/Web/API/Document/adoptedStyleSheets)). Lit's own Shadow DOM docs likewise recommend constructable stylesheets over `<style>`-in-`<template>` specifically "for sharing styles across multiple components" ([Lit docs — Working with Shadow DOM](https://lit.dev/docs/components/shadow-dom/)).

**Bottom line**: Constructable stylesheets are safe to rely on cross-browser today (Baseline since March 2023) and are the correct, spec-sanctioned mechanism for avoiding N-times style duplication across many `blank` component instances.

## 4. SSR and hydration

- **Declarative Shadow DOM (DSD) spec**: defined in the WHATWG HTML spec as the `shadowrootmode` attribute on `<template>`, with enumerated values `open`/`closed`; missing/invalid value defaults to "None" (no shadow root created) — i.e. it is opt-in per template ([WHATWG HTML spec §template.shadowrootmode](https://html.spec.whatwg.org/multipage/scripting.html#attr-template-shadowrootmode)). A `<template shadowrootmode="open">` inside a host element is parsed by the browser directly into an attached shadow root with no JavaScript required.
- **Browser support**: Declarative Shadow DOM reached **Baseline "Newly available" as of August 5, 2024**, working in Chrome 111+/Edge 111+ (streaming-capable `shadowrootmode` version; an older non-standard `shadowroot` attribute existed from Chrome 90), Firefox 123+, and Safari 16.4+ ([web-features / MDN browser-compat data, corroborated via WebKit blog announcement](https://webkit.org/blog/13851/declarative-shadow-dom/); compat figures via [web-features declarative-shadow-dom entry](https://github.com/web-platform-dx/web-features/blob/main/features/declarative-shadow-dom.yml)). This means a static site can genuinely serve pre-rendered shadow-DOM markup (including scoped styles) that renders correctly before any JS executes, in all three engines.
- **Lit SSR maturity**: Lit's own docs classify `@lit-labs/ssr` as **Labs/experimental**: "This package is part of the Lit Labs family of experimental packages," directing users to the Labs guidance page before using it in production; the package's own "Library status" section states it is "under active development with some notable limitations," including unsupported async component work, shadow-DOM-only component support, incomplete DSD browser support requiring a polyfill (at time of writing), and open questions around custom-element interop ([Lit docs — SSR overview](https://lit.dev/docs/ssr/overview/); [@lit-labs/ssr on npm](https://www.npmjs.com/package/@lit-labs/ssr)). Lit SSR is **not** a stable, GA feature per Lit's own classification.
- **Framework/tool support for server-rendering Web Components**:
  - **Astro**: natively supports plain custom elements with zero framework overhead — you `customElements.define()` a class extending `HTMLElement` and use the tag directly in `.astro` templates; Astro's docs give a full worked example (`AstroHeart`) and note this avoids shipping any UI-framework JS ([Astro docs — Client-side scripts](https://docs.astro.build/en/guides/client-side-scripts/)). This is plain custom elements (progressive enhancement), not DSD/Lit-SSR specifically — Astro does not need to server-render *shadow* content to support this pattern.
  - **Eleventy**: the official `eleventy-plugin-webc` explicitly supports "server-rendering... without duplicating author-written markup," and is designed to compose with `is-land` for hydration; requires Eleventy ≥2.0.0 ([11ty/eleventy-plugin-webc README](https://github.com/11ty/eleventy-plugin-webc)).
  - Neither Astro's nor Eleventy's primary docs claim built-in Lit-SSR or DSD-emission as a first-class, zero-config feature; both patterns above are either plain-custom-element progressive enhancement (Astro) or a bespoke component syntax with its own server-rendering model (Eleventy WebC), not "invoke Lit SSR and get DSD out."

**Bottom line**: DSD itself (the platform primitive `persona` would rely on) is production-viable today — Baseline since August 2024, all three engines. Lit's *own* SSR tooling is explicitly experimental/Labs per Lit's own docs, so if `blank` is built with Lit, getting pre-rendered shadow-DOM markup out of it for a static site currently means relying on non-stable tooling; a vanilla-custom-element approach sidesteps this because DSD is a platform feature independent of any component-authoring library, and Astro/Eleventy both have first-party patterns for plain custom elements without needing a stable Lit-SSR story.

## 5. Theming API

- **CSS custom properties cross the shadow boundary by inheritance**: a custom property declared with `--name` "always inherits the value of its parent" as an ordinary (regular, non-`@property`-registered) custom property, and this inheritance is not blocked by the shadow boundary — a value set on `:root` or on the shadow host in light-DOM CSS is inherited into the shadow tree exactly as normal CSS inheritance would carry it into any descendant ([MDN — Using CSS custom properties](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_cascading_variables/Using_CSS_custom_properties)). This is the sanctioned mechanism for a consumer to theme values (colors, spacing) inside a Shadow-DOM component without piercing encapsulation. Registering a property via `@property` with `inherits: false` is the documented way to opt a specific custom property *out* of crossing the boundary.
- **`::part()`**: styles elements *inside* a shadow tree from outside it, but only for elements the component author has explicitly marked with the `part="name"` global HTML attribute — "the shadow host component must explicitly expose internal elements" this way; part names behave like classes (shareable, multiple per element); parts are visible only to the *direct* parent DOM tree by default, and the `exportparts` attribute is required to re-expose a part further up through nested shadow trees. Baseline widely available since July 2020 ([MDN — `::part()`](https://developer.mozilla.org/en-US/docs/Web/CSS/::part)).
- **`::slotted()`**: used *inside* a shadow tree's own CSS to style light-DOM content that has been slotted in; matches only the top-level slotted element itself (not its descendants), does not accept descendant combinators inside the selector, and does not match text nodes. Baseline widely available since January 2020 ([MDN — `::slotted()`](https://developer.mozilla.org/en-US/docs/Web/CSS/::slotted)).
- **What a consumer needs, concretely, to restyle `blank` for a different project**: the library author must deliberately (a) expose a documented set of CSS custom properties as the theming API surface (colors, spacing, fonts) at sensible defaults on `:host`, since these are the only values that cross the boundary automatically; (b) add `part="..."` attributes to any internal elements a consumer should be able to restyle structurally, since nothing is exposed by default; (c) write `::slotted()` rules inside the component's own stylesheet for any light-DOM content the consumer projects in via `<slot>`, since the consumer's own CSS cannot reach slotted-content styling from outside the shadow tree in the general case. None of this is automatic — it is API design work the library author must do per-component.

**Bottom line**: CSS custom properties are the low-friction default theming channel (automatic inheritance, no author work beyond documenting variable names); `::part()` and `::slotted()` are opt-in, per-element mechanisms that require the library author to deliberately annotate markup — theming is not "free" with Shadow DOM, it is a designed, published surface exactly like any other public API.

## 6. Packaging a Web Components library to npm

- **ESM-only expectations**: Node.js's package-exports documentation shows the `"exports"` field as the mechanism for defining and restricting entry points, and explicitly discusses conditional exports (`"import"` vs `"require"`) for dual CJS/ESM support; Node's own docs do not mandate ESM-only, and in fact recommend keeping a `"main"` field alongside `"exports"` "for projects using an older version of Node.js or a related build tool" for compatibility ([Node.js docs — packages.html#exports](https://nodejs.org/api/packages.html#exports)). An ESM-only publish (`"type": "module"`, `"exports"` pointing only at `.js`/`.mjs` ESM files, no `"require"` condition) is a valid, spec-supported choice but is an explicit narrowing relative to what Node documents as the safer default (dual-publish or CJS-fallback via `"main"`).
- **Individual entry points vs single bundle**: the `"exports"` field supports arbitrary subpath maps (`"./button": "./src/button.js"`) and glob/pattern subpaths (`"./features/*.js"`), so a package can expose one entry point per component alongside (or instead of) a single barrel bundle ([Node.js docs — packages.html#exports](https://nodejs.org/api/packages.html#exports)).
- **`customElements.define` side-effect problem and tree-shaking**: webpack's own docs define a "side effect" as "code that performs a special behavior when imported, other than exposing one or more exports," and document the `package.json` `"sideEffects"` field (`false` = safe to prune anything unused; array = explicit list of files with side effects that must always be kept) as the mechanism bundlers use to decide what's prunable ([webpack docs — Tree Shaking](https://webpack.js.org/guides/tree-shaking/)). A module that calls `customElements.define(...)` at import time is a side effect by this definition — the registration has an effect (registering a global tag) independent of any exported binding being used. Marking such a module `sideEffects: false` is exactly the "incorrectly marking modules as side-effect-free" pitfall webpack's docs warn about, since a bundler would then be permitted to drop the defining module if nothing appears to import a named export from it, silently breaking the custom element registration. This is the concrete tension between (a) an "auto-registering" entry point (import for effect: `import 'blank/button'` registers `<blank-button>` globally) and (b) tree-shaking, which by design tries to eliminate imports whose exports go unused — the two are only compatible if the package's `sideEffects` field lists exactly the auto-registering entry files so bundlers never drop them, or if the library instead exports an explicit `register()`/class + lets the consumer call `customElements.define()` themselves (fully side-effect-free, tree-shakeable, but no longer "auto-registering").
- **TypeScript declarations**: standard practice is compiling `.d.ts` files alongside JS output and pointing `"types"`/`"exports"."types"` at them; this is TypeScript-toolchain convention rather than a Web-Components-specific concern, and is not separately spec'd beyond TS's own compiler output and Node's `"exports"`/`"types"` condition support.
- **Custom Elements Manifest (`custom-elements.json`)**: a JSON-Schema-defined, machine-readable format describing a package's custom elements (tags, attributes, properties, events, CSS custom properties, slots, parts) so that "developers using custom elements should be able to get full-featured IDE support including auto-completion, hover-documentation, unknown symbol warnings" in editors, plus documentation-site generation and framework-integration tooling; current schema version is **2.1.0** (released May 6, 2024); packages reference their manifest file via a `"customElements"` field in `package.json` ([webcomponents/custom-elements-manifest spec repo](https://github.com/webcomponents/custom-elements-manifest)). It is generally produced by static analysis of the TS/JS source (e.g. the `@custom-elements-manifest/analyzer` tool in the ecosystem) rather than hand-authored.

**Bottom line**: ESM-only is a legitimate but explicitly narrower-than-documented-default choice per Node's own packaging docs; per-component entry points are fully supported via `"exports"` subpaths; auto-registration-on-import and clean tree-shaking are in direct tension and must be resolved deliberately via the `sideEffects` field (or by not auto-registering); and Custom Elements Manifest (schema v2.1.0) is the standardized, spec'd path to IDE/editor support and should be generated from source, not hand-maintained.

## 7. Framework interop

- **React 19**: shipped **full custom-element support**, passing all [Custom Elements Everywhere](https://custom-elements-everywhere.com/) tests (previously React scored 67% pre-19; React 19 scores 100%, per the benchmark's own published results) ([React docs — React v19 blog post](https://react.dev/blog/2024/12/05/react-19); [Custom Elements Everywhere — React results](https://custom-elements-everywhere.com/libraries/react/results/results.html)).
  - **Props vs. attributes**: React's own v19 release notes state the strategy precisely — during SSR, "props passed to a custom element will render as attributes if their type is a primitive value like string, number, or the value is true. Props with non-primitive types like object, symbol, function, or value false will be omitted." During client rendering, "props that match a property on the Custom Element instance will be assigned as properties, otherwise they will be assigned as attributes" ([React docs — React v19](https://react.dev/blog/2024/12/05/react-19)).
  - **Event handling**: React 19 adds native support for custom events via the conventional `on<EventName>` prop pattern, replacing the prior workaround of manually attaching listeners via a ref ([React docs — React v19](https://react.dev/blog/2024/12/05/react-19)).
- **Astro**: has documented, first-class support for defining and using native custom elements directly in `.astro` templates, with a worked example in its own docs (§4 above) ([Astro docs — Client-side scripts](https://docs.astro.build/en/guides/client-side-scripts/)); Astro's framework-components docs additionally note that every supported UI framework (React, Preact, Svelte, Vue, Solid) already knows how to render/manipulate DOM elements including custom elements, so cross-framework consumption inside Astro islands is not blocked.
- **Svelte**: compiles components to custom elements via the `customElement: true` compiler option plus a `<svelte:options customElement="tag-name" />` declaration; by default compiles with `accessors: true` so props are exposed as both DOM properties and (where possible) attributes, and exposes the host element inside the component via the `$host` rune — this is Svelte's own *authoring* story (building custom elements), and separately Svelte scores at or near 100% on Custom Elements Everywhere as a *consumer* of others' custom elements ([Svelte docs — Custom elements](https://svelte.dev/docs/svelte/custom-elements); [sveltejs/custom-elements-everywhere](https://github.com/sveltejs/custom-elements-everywhere)).
- **Vue**: documented custom-element consumption requires `compilerOptions.isCustomElement` (a tag-name predicate) so Vue's compiler skips its own component-resolution for those tags — configurable per build tool (Vite/webpack/on-the-fly compile); once configured, Vue "automatically checks for DOM-property presence and prefers setting properties over attributes," with a `.prop` modifier for edge cases. Vue scores 100% on Custom Elements Everywhere. Vue also documents its own `defineCustomElement()` API for the reverse direction (authoring Vue components as custom elements), including SFC `.ce.vue` files that inline styles into the shadow root ([Vue docs — Vue and Web Components](https://vuejs.org/guide/extras/web-components.html)). Vue's docs separately flag that *native* custom-element SSR "typically requires simulating the DOM in Node.js and serializing it," which they present as less efficient than Vue's own string-concatenation SSR for Vue-native components — relevant context if a `blank` consumer wanted Vue-driven SSR of `blank` elements specifically, though not a blocker for using them client-side.

**Bottom line**: no mainstream consumer framework forecloses Web Components as of 2026. React was the last holdout and closed the gap in React 19 (100% on Custom Elements Everywhere, documented props/attributes/events strategy in React's own release notes); Astro, Svelte, and Vue all have long-standing, documented, high-compatibility interop in both directions (consuming and, where relevant, authoring).
