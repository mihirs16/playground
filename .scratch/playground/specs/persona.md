# Spec: persona

Status: ready-for-agent

The public website — the face presented to the world. `persona` bakes blog prose,
the blog index, and profile content at build time from `custodian`, loads live
status (Steam, GitHub) at runtime in the browser, and is built with `blank`.

This spec synthesises the resolved decision tickets `23` (blog delivery model),
`15` (framework), and `16` (blog delivery, crawlability & permalinks), grounded
in the `03` domain model, ADR-0001 (hosting posture), and the upstream contracts
from `09` (custodian API), `14`/`21`/`22` (blank inventory, rendering foundation,
accessibility), and `12` (derived-data freshness). Where a later ticket revised
an earlier position, the revised position is stated here as the single source of
truth. Companion spec: `custodian.md` (the API `persona` consumes).

## Problem Statement

The author needs a personal website that presents long-form blog posts, a
profile (about / experience / skills / resume link / curated projects), and a
pair of live-status widgets (Steam currently-playing, GitHub activity). The
deprecated Next.js + Notion site made this painful in ways `persona` must not
repeat:

- **A shared blog link previewed as a blank page.** If prose is fetched in the
  browser, the initial HTML is an empty shell; most link-preview scrapers
  (Slack, iMessage, WhatsApp, Mastodon, LinkedIn) and non-Google crawlers run no
  JavaScript, so a shared post unfurls to nothing and search engines index an
  empty document.
- **Content was coupled to code.** Presentation, content, and secrets lived
  together, so every content concern dragged the build and the client bundle in
  with it.

The author wants a public site where blog permalinks are real, crawlable,
fast-painting URLs that survive a hard refresh; where a post shared into a chat
app unfurls with a title and preview; where live status appears when it is fresh
and simply vanishes when it is not; and which runs as cheap static objects with
no server to keep alive — while consuming `blank` through its published API so
that library never silently becomes persona-shaped.

## Solution

`persona` is a **pure static site generated by Astro (`output: 'static'`)** with
**no render tier**. At build time it fetches `custodian`'s public `/v1` read
surface and bakes:

- every **listed** log into a real prerendered file at `/logs/<slug>/`,
- the **blog index** page,
- **profile** content into the pages that show it,
- an **RSS 2.0** feed at `/rss.xml`,
- per-page **OG/meta** tags in each page `<head>`.

The output is a directory of static files synced to a private S3 bucket behind
CloudFront (ADR-0001 / `19`). Blog prose sits in the initial HTML payload, so
crawlers, link-unfurlers, and first paint all get real content with no
JavaScript — the empty-shell failure mode is designed out. `custodian` is a
**build-time-only dependency** for baked content; it is off the reader's request
path, so a `custodian` outage cannot blank a permalink.

The only runtime fetches are the **decorative derived-status widgets** (Steam,
GitHub), implemented as plain client-side custom elements that fetch `custodian`
on `connectedCallback` and **hide themselves when there is no data**. This is the
one place instant freshness still matters and is preserved.

Publishing a batch of posts is a **manual rebuild** the author runs (a `just` /
deploy recipe). This deliberately reintroduces rebuild-to-edit for blogs,
consciously reframed as **editorial batching** — the author controls when a batch
goes live. `broom` and `custodian` stay completely ignorant of `persona`; the
coupling is one-directional and build-time only.

## User Stories

### Reading blogs — the crawlable, permalinked reader experience

1. As a reader, I want to open a blog permalink like `/logs/<slug>/` directly, so that a shared or bookmarked link resolves as a real page.
2. As a reader, I want a hard refresh on a blog permalink to work, so that the page is a real file, not a client-router state I can only reach from the index.
3. As a reader, I want the blog post's prose to be present the instant the page loads, so that I read content without waiting on a client-side fetch.
4. As a reader with JavaScript disabled or on a slow device, I want the full post text to still render, so that reading never depends on hydration.
5. As a reader, I want a blog index listing the published posts, so that I can browse what has been written.
6. As a reader, I want the index to show each post's title and, when present, its description and metadata (reading time, tags, date), so that I can decide what to open.
7. As a reader, I want an unlisted draft to be reachable only if I have its exact slug link and never to appear in the index, so that drafts are shareable but not advertised.
8. As a reader, I want blog pages to remain readable during a `custodian` outage, so that infrastructure trouble behind the scenes never blanks the site.

### Sharing and discovery — crawlers, unfurlers, feeds

9. As a link-preview scraper (Slack, iMessage, LinkedIn, Mastodon) that runs no JavaScript, I want title/description/image meta in the initial HTML `<head>`, so that a shared post unfurls with a real preview.
10. As a non-Google crawler (Bing, DuckDuckGo) that does not execute JavaScript, I want the post prose in the served HTML, so that the page is indexable.
11. As a reader, I want a post with no author-written description to simply omit the description meta tag, so that I never get a mangled auto-truncated preview.
12. As a site, I want a single site-wide default OG image on every post, so that shares are branded without needing a per-post image field.
13. As a site, I want standard OG/Twitter boilerplate (canonical URL, `og:type=article`, `og:site_name`, `twitter:card=summary_large_image`) baked into each post head, so that previews are well-formed across platforms.
14. As an RSS reader, I want an `/rss.xml` feed over the published posts (title, description, permalink, date), so that I can subscribe without visiting the site.
15. As the author, I want the feed and the index to be generated over the same set of listed slugs the pages are built from, so that they can never drift out of sync with what was published.

### Profile — the about / experience / skills / projects surface

16. As a reader, I want to see the profile content (about, experience, skills, curated projects, resume link) rendered on the site, so that I learn who the author is.
17. As a reader, I want the `about` markdown rendered as prose, so that it reads like the rest of the site.
18. As a reader, I want the curated project showcase presented as a deliberately authored, ordered list, so that it reads as editorial — distinct from the observed GitHub activity feed.
19. As the author, I want profile content baked at build time from `custodian`, so that a future QnA bot can answer from the same API-backed profile, and all content stays in one owned store.
20. As the author, I want editing profile to require a rebuild, so that the low-churn yearly edit is an accepted, deliberate trade — not a surprise.

### Live status — the derived-data widgets

21. As a reader, I want to see what the author is currently or recently playing on Steam, so that the site feels alive.
22. As a reader, I want to see recent GitHub activity, so that I can see what the author is demonstrably working on.
23. As a reader, I want a status widget to fetch its data in the browser at runtime, so that it reflects near-current state without the whole site being rebuilt.
24. As a reader, I want a status widget with no data to be absent entirely rather than showing an empty or broken box, so that the page never displays a hollow placeholder.
25. As a reader, I want the widget copy to say "recently active" rather than "live" or "now", so that the honestly-imprecise freshness of a polled feed is not overstated.
26. As a reader, I want the widget to decide for itself when a stale timestamp has become a lie and stop presenting it as current, so that I am never shown old data dressed as fresh.
27. As a reader, I want the curated-projects showcase (authored) and the GitHub activity feed (observed) to render as visibly different things, so that I am not misled into thinking an observed feed was hand-curated.

### Look and feel — consuming `blank`

28. As a reader, I want the whole site to share one monotone, whitespace-heavy visual identity, so that it reads as a single coherent surface.
29. As a reader, I want a dark theme as a first-class experience, so that the site is comfortable to read in either mode.
30. As a reader, I want long-form prose set in the reading serif with authored casing preserved, while chrome and headings are lowercased mono, so that the one class of text meant to be read normally is visually marked as such.
31. As the author, I want `persona` to compose its page furniture (navbar, hero, about, experience card, project card, skills, footer, post-list item, status line) from `blank`'s primitives, so that field-aware layout lives in `persona` and only reusable primitives live in `blank`.
32. As a reader, I want a log body to be able to embed a live `blank` component (e.g. a post about `blank` showing a real `<blank-stat>`), so that writing about the library can demonstrate it.

### Build, deploy, and operability

33. As the author, I want a single command to build and deploy the site, so that publishing a batch of posts is one deliberate gesture.
34. As the author, I want a failed `custodian` fetch during the build to fail the build loudly, so that I never ship a site with silently missing baked content.
35. As the author, I want `broom` and `custodian` to be completely unaware of `persona`, so that the content pipeline stays one-directional and I alone decide when content goes live.
36. As the author, I want `persona` to depend on the local `blank` via the workspace and import only through `blank`'s published `exports`, so that dev/build stay on head while the publish-forcing-function keeps `blank`'s API honest.
37. As the author, I want clean URLs (`/logs/<slug>/`, never `.html` in the address bar), so that permalinks look intentional and stay stable.

## Implementation Decisions

### Framework and delivery model (`15`, `23`)

- **Astro, `output: 'static'` — a pure SSG, no render tier.** Chosen on the
  merits as the lowest-ceremony fit for the fixed shape (build-time bake,
  prose-in-payload, client-hydrating `blank` chrome, client-fetch derived
  widgets). Astro *reduces* bespoke surface — the markdown pipeline, blog
  routing, and index generation come for free — so "polyglot is incidental" does
  not bite. The minimal Vite/11ty case was considered and rejected: it trades a
  dependency you would learn anyway for a pile of glue you would own forever. SSR
  on a running server and ISR/on-demand-revalidation were ruled out upstream
  (`23`) — `persona` stays a static-object host and `custodian` stays off the
  per-request reader path.
- **Blogs are build-time SSG.** Prose is baked into the initial HTML payload
  (all-crawler SEO + fast paint). `custodian` is a **build-time dependency**: the
  build fetches listed logs from the public `/v1` read API; `custodian` stays
  pure-JSON, off the reader path.
- **Publish trigger is manual** — a root `just` / deploy recipe the author runs
  to batch posts live. **No `custodian`→`persona` webhook, no timer.** This
  reintroduces rebuild-to-edit *for blogs*, accepted consciously as editorial
  batching. The freshness half of `custodian`'s motivation still applies with
  full force to derived data (below).

### Routing and output shape (`15`)

- **Fully static routing, no client-side router.** Each log is a real
  prerendered file via `getStaticPaths()` over `custodian`'s slugs (`09` — slug
  is a log's sole identity, maps 1:1 to the output path). Deep permalinks survive
  a hard refresh; there is no SPA router and no client navigation.
- **`build.format: 'directory'`** gives clean `/logs/<slug>/` URLs (no
  `.html`/`index.html` in the address bar).
- **A `deed`-owned CloudFront Function (viewer-request) rewrites
  `/logs/<slug>/` → `/logs/<slug>/index.html`.** Because `19` fronts a **private
  S3 bucket via CloudFront + OAC** (not a public S3 website endpoint), the raw-S3
  origin does not auto-resolve subfolder indexes. The ~15-line rewrite is the
  mainstream AWS pattern (OAC + CloudFront Functions) and deliberately avoids the
  public-website-endpoint shortcut that would let clients bypass CloudFront and
  undercut `10`'s edge WAF/rate-limiting and `19`'s perimeter. *This is a `deed`
  line item, recorded here as the contract `persona`'s output depends on — not
  `persona`'s implementation.*

### Content fetching at build (`15`, `23`, `09`)

- **Profile, blog index, and blog prose bake at build** via build-time `fetch()`
  against `custodian`'s **public `/v1`** read surface — no admin token in the
  build. A `custodian`-down build **fails loudly**, which is correct.
- **Profile stays in `custodian`, baked at build — with a shifted rationale.**
  `03`'s original "escape rebuild-to-edit" reason is dead (`23` reintroduced
  rebuild-to-edit for all baked content). What keeps profile in `custodian` is a
  **retrieval** rationale: a future QnA bot answers from the profile via the same
  public API, and a bot reads an API/queryable store, not build artifacts. So
  `03`/`08`/`09`/`17` are **not** revised; moving profile to repo files was
  considered and rejected on this basis. The QnA bot is out of scope here — it is
  the standing reason profile stays API-backed, not a deliverable.
- **Reads use the `09` contract as-is:** `GET /v1/logs` (paginated index,
  listed-only, body omitted), `GET /v1/logs/{slug}` (full body, any state),
  `GET /v1/profile/{key}`, `GET /v1/integrations/{source}`. `persona` fetches
  media bytes only from the CDN URL, never from the API.

### Markdown rendering and the fate of `<blank-markdown>` (`16`, revises `14`)

- **`<blank-markdown>` is dropped from v1 (option b — dissolves into the build).**
  Under SSG the build-time markdown renderer **must** be Astro's own
  **remark/rehype** pipeline; rendering a Lit component at build would drag in
  `@lit-labs/ssr`, which `21` banned. `<blank-markdown>`'s only consumer was the
  blog path, which SSG removed, so a persona-owned component would ship with zero
  callers. Markdown-to-HTML is a **build step, not a component**. `custodian`
  still stores raw GFM-core markdown; only the rendering *location* moves. A
  runtime-markdown component graduates from fog later only if a real second
  surface (live preview, comment box) needs one. **This revises `14`** (drops
  `<blank-markdown>` from the inventory).
- **Blog prose is light-DOM semantic HTML** styled by `blank`'s global base /
  tokens stylesheet (`21`'s light-DOM-prose exception), so prose is crawlable,
  fast-painting, and consistently styled.

### Embedding live `blank` in log bodies — `rehype-raw` (`16`, `15`, `03`)

- **`rehype-raw` (raw-HTML passthrough) is enabled** so a log body can embed live
  `blank` components (e.g. a real `<blank-stat>` inside a post about `blank`).
  Raw HTML is GFM-core-legal (`03`), so this is allowed grammar, not novel
  syntax.
- This is normally an XSS vector; it is safe here **only** because of the
  **single-trusted-author** invariant. **That assumption is documented in both
  this spec and an inline comment at the pipeline config**, so the caveat travels
  with the code and cannot rot into an unexamined hole if authorship ever
  changes.

### OG / meta tags (`16`)

- Baked **build-time into each Astro page `<head>`**. Set per post:
  - **title**;
  - an **optional `description`** — omitted entirely when the log has none (an
    absent preview beats a mangled auto-truncated one);
  - a **single site-wide default OG image** (monotone card) — no per-post image
    field (that stays fog, being the classic never-populated field);
  - standard boilerplate: **canonical URL, `og:type=article`, `og:site_name`,
    `twitter:card=summary_large_image`**.

### The `description` field (`16`, revises `03`/`08`/`09`/`17`)

- A dedicated **optional plain-prose `description`** graduates from `03` fog onto
  the `log` record, sourced from `custodian` and used for OG description and
  (later) blog-list excerpts. **`subtitle` stays editorial** (a preface line or
  quote, part of the reading experience) and must **not** be conscripted as an
  SEO summary. This revises `03` (un-defers the field), `08` (storage column),
  `09` (API field), `17` (`broom logs new` metadata prompt) — all recorded in
  `custodian.md`; `persona` is the consumer.

### RSS feed (`16`)

- **RSS 2.0 in v1**, generated build-time at `/rss.xml` via `@astrojs/rss` over
  the same `getStaticPaths()` slug set — no new data source, no runtime tier.
  RSS 2.0 over Atom for widest reader support; the correctness edge does not
  matter at this scale. Reuses title / `description` (absent → fine) / permalink.

### Consuming `blank` (`15`, `21`, `14`)

- **Workspace dependency on local `blank` (`workspace:*`, per `13`)** so dev/build
  are always on head — which also lets logs *about* `blank` render live `blank`
  components. The **forcing-function invariant** (publishing keeps `blank`'s API
  from going persona-shaped) is preserved by importing **only through `blank`'s
  published `exports` map** (`21`'s per-component subpaths + barrel), never a deep
  `../blank/src/...` reach.
- **Registration:** `persona` loads `blank`'s auto-registering `@customElement`
  entry (`21`) in a **client-side script**. Astro emits inert `<blank-*>` tags at
  build; the browser upgrades/hydrates them — matching `21`'s posture B, so
  `@lit-labs/ssr` stays absent.
- **Base / tokens stylesheet imported once, globally** in Astro's root layout. It
  styles the light-DOM blog prose *and* supplies the custom-property tokens that
  cross into `blank`'s shadow chrome (`21`'s only cross-boundary channel).
- **Page furniture is `persona`-owned composition** (`14`): navbar, hero, about,
  experience card, curated-project card, skills, footer, post-list item, and the
  status *line* (label + dot) are compositions of `blank`'s six primitives + base
  headings. Each knows its own *fields*; none of that field-awareness leaks into
  `blank`.

### Derived-status widgets (`15`, `12`, `14`)

- **Plain client-side custom elements, not Astro `client:*` islands.** Because
  `blank` components are raw custom elements (not framework components), they
  hydrate via native custom-element upgrade, not Astro directives.
- Each widget **fetches `custodian` on `connectedCallback`** (`GET
  /v1/integrations/{source}`) and **hides itself on empty** (`12` — empty-array
  → widget absent). The status surface is an instance of `<blank-badge>`
  (`14`), not its own component.
- **`persona` owns the staleness policy.** `custodian` has zero opinion on data
  age and always carries a fetch timestamp (`12`); `persona` owns the "recently
  active → stale" threshold and the copy ("recently active", never "live"/"now").
- Idle and "source briefly unreachable" are indistinguishable by design (`12`) —
  the honest statement in both cases is "nothing new since X".

### Accessibility floor (`22`)

- `persona` owns **heading order, alt text, and the actual `aria-label` values**
  it passes to `blank`'s icon buttons (`22`'s split: `blank` provides the
  mechanism; `persona` provides the values). Real links are real `<a>`; the base
  stylesheet does not suppress native focus. Full WCAG audit / contrast tests /
  monotone focus-ring design are out of scope (`22` fog).

### Deploy shape (context — `19`, `01`)

- Build output is synced to a **private S3 bucket behind CloudFront + OAC**;
  publish is a **laptop `s3 sync` + CloudFront invalidation** under SSO creds
  (`19`), triggered by the same manual rebuild recipe. No long-lived render tier,
  no server. *Provisioning the bucket, distribution, OAC, and the index-rewrite
  CloudFront Function is `deed`'s work — recorded here as the contract, not
  `persona`'s implementation.*

## Testing Decisions

**What makes a good `persona` test:** it asserts on **externally observable
output** — the bytes of the built site and the rendered DOM a reader actually
gets — never on component internals, private helpers, or which remark plugin ran.
A test should read like a crawler, an unfurler, or a reader, because those are
`persona`'s real clients.

**Two seams, drawn where `persona`'s two runtimes actually are.** The build and
the browser are genuinely different environments; the derived widgets never
appear in the build output, so a single seam cannot honestly cover both. Both
seams are the highest available in their runtime, and both are established
patterns (Astro's own suite asserts on compiled output; Web Components are tested
in a real browser via a fixture harness).

### Seam 1 — the build output (the SSG half)

- Run the **real Astro build** against a **faked `custodian` `/v1`** HTTP surface
  (a local stub / MSW the build's `fetch()` hits — a fixed set of logs, profile
  records, and integration payloads), then assert on the emitted `dist/`.
- **Assertions (reader/crawler-observable):**
  - blog prose is present in the served HTML payload (not an empty shell);
  - each listed slug produces a real file at `dist/logs/<slug>/index.html`;
    unlisted slugs produce a reachable file but never appear in the index;
  - the blog index lists exactly the listed posts, with metadata;
  - each post `<head>` carries title + boilerplate OG/Twitter tags + the
    site-wide default OG image; a log **with** a `description` emits the meta tag,
    a log **without** one **omits** it;
  - `dist/rss.xml` exists and is well-formed over the same slug set;
  - profile content is baked into the pages that show it;
  - a raw-HTML `<blank-*>` tag in a log body passes through to the output
    (`rehype-raw`), rather than being escaped or stripped;
  - a build against a **down `custodian`** (fake returns an error) **fails
    loudly** rather than emitting a site with missing content.
- **Framework:** **Vitest** driving Astro's build (programmatic `build()` or the
  CLI) + filesystem/HTML assertions. This is Astro's own testing posture
  (snapshot / build-output assertion); `astro-component-tester` is direct OSS
  prior art for the "build a component, assert the output" shape.

### Seam 2 — the derived-status custom elements (the runtime half)

- Mount the widget custom element in a **real browser DOM** with a **faked
  `fetch`**, then assert the reader-observable outcome.
- **Assertions:** renders status when data is present; **hides itself when the
  integration payload is empty** (`12`); applies `persona`'s staleness threshold
  to the fetch timestamp (fresh → shown as current; past-threshold → not
  presented as current); tolerates a failed/timed-out fetch by staying hidden
  rather than erroring.
- **Framework:** **`@open-wc/testing`** on **Web Test Runner** (real browser via
  Playwright/Puppeteer), with **Sinon** stubbing `fetch`. Note the documented
  gotcha: `connectedCallback` fires immediately on `fixture()`, so the `fetch`
  stub must be installed **before** mounting; then `await el.updateComplete`.

**Prior art:** there is no existing `persona` suite yet — this spec establishes
the pattern. Seam 1 mirrors Astro's own build-output/snapshot testing; seam 2
mirrors the standard `@open-wc/testing` fixture + Sinon-stub flow used across the
Web Components ecosystem. The `custodian` spec's single-HTTP-boundary seam is the
sibling precedent for "drive it black-box through its real contract."

## Out of Scope

- **Building `custodian`, `broom`, `blank`, or `deed`.** Where this spec touches
  them it records the *contract*, not their implementation.
- **The CloudFront Function index-rewrite, the S3 bucket, CloudFront, and OAC** —
  `deed`'s work (`19`); `persona` only produces the static output that assumes
  them.
- **ISR / on-demand revalidation / SSR / any running render tier** — ruled out by
  `23`; `persona` is static-only.
- **A `custodian`→`persona` webhook or publish timer** — publish is a manual
  rebuild; the coupling stays one-directional.
- **A runtime `<blank-markdown>` component** — dropped from v1 (dissolves into
  the Astro build); graduates from fog only if a real second runtime-markdown
  surface appears.
- **Per-post OG image field** — a single site-wide default only; per-post image
  stays fog.
- **Conscripting `subtitle` as an SEO summary** — `subtitle` is editorial;
  `description` is the SEO source.
- **A QnA bot / assistant over the profile** — the standing *reason* profile
  stays API-backed, not a deliverable here.
- **The full page/route inventory beyond blogs, profile, and the status
  surface** — and the dropped v1 status page (`11`) — remain persona-inventory
  fog.
- **Full accessibility** (WCAG 2.2 AA audit, contrast tests, dark-theme +
  `#FBFF20`-text-background verification, monotone focus-ring design) — `22` fog;
  v1 ships only the cheap floor.
- **A blog-list excerpt UI, manual derived-data override/pin, and a
  derived-data timeline** — all fog upstream.
- **The cutover from the deprecated Netlify deployment** (TTL lowering, cert
  validation, avoiding a no-site window) — a separate task.

## Further Notes

- **The crawlability trade this feature set was created to force is already
  resolved upstream** (`23`: SSG won). `persona`'s job is to *realise* that
  resolution correctly — prose in the payload, real permalink files, build-time
  OG tags — not to re-litigate runtime-vs-build delivery.
- **Two dependencies on `custodian`, two lifetimes:** baked content (logs,
  profile, index) is a **build-time** dependency and is off the reader path;
  derived widgets are a **runtime** dependency and degrade to *hidden* on
  failure. A `custodian` outage therefore cannot blank a blog permalink — only
  quietly drop a status widget.
- **Why profile lives in `custodian` at all:** do not re-derive the freshness
  argument — it is dead (`23`). The live rationale is **retrieval** (a future
  QnA bot reads the same public API) plus keeping all content in one owned store.
- **The single-trusted-author invariant is load-bearing.** `rehype-raw` is safe
  *only* under it. The invariant is documented here and at the pipeline config
  inline; if authorship ever becomes multi-writer, raw-HTML passthrough must be
  revisited before anything else.
- **The forcing function must not be bypassed.** Importing `blank` only through
  its published `exports` is what keeps its API from silently becoming
  persona-shaped; a deep `../blank/src` import would quietly defeat the whole
  reason `blank` is published.
